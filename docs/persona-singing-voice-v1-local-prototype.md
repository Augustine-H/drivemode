# Persona Singing Voice v1 — 무료 로컬 검증

검증일: 2026-10-09. 기준 음색은 사용자가 지정한 **페르소나별 xAI 목소리**다. Google TTS 재생 음색을 기준으로 삼지 않는다.

## 현재 상태

로컬 실험 코드와 실제 비교 음원이 준비됐다. **NAS·Grok 1.34.8에는 아직 적용하지 않았다.** 생성마다 동일한 목소리를 유지한다고 보증하지 않으며 사용자 청취 확인도 아직 받지 않았다. 버전 변경, GitHub 업로드, NAS 재게시도 하지 않았다.

검증 경로는 `ACE-Step 무료 노래 생성 → Demucs 보컬 분리 → Seed-VC 가창 음색 변환 → 기존 반주와 재결합 → WAV/MP3 검증`이다. 추가 유료 API 호출은 0회다. xAI의 공식 문서에 공개된 Ara/Eve 음성 샘플을 참조로 사용했다. 참조와 모델은 로컬 runtime에만 보관한다.

## 비교 결과와 한계

동일한 한국어 자체 작성 가사, 30초, 생성 시드 1042/2026으로 기준 음원·Ara 참조·Eve 참조 총 6개 비교 음원을 만들었다. 복구 전 HTTP 연결 오류로 접수된 Ara 작업 1개가 추가로 실행돼 실제 ACE-Step 생성은 7회다. 이 추가 작업은 비교에서 제외했다.

ACE-Step의 `reference_audio`만 사용하면 Ara 참조 결과도 Eve 참조와 더 유사하게 측정됐다. 따라서 참조 조건만으로 페르소나 가창이 완성됐다고 판단하지 않았다. 이어서 각 기준 음원의 분리 보컬을 Ara/Eve로 변환하는 Seed-VC 비교 4개를 실행했다.

| 변환 | 로딩 포함 변환 시간 | CUDA 최대 할당 | 프로세스 최대 RAM |
| --- | ---: | ---: | ---: |
| Ara, 시드 1042 | 29.466초 | 2703.38 MiB | 2402.86 MiB |
| Eve, 시드 1042 | 18.058초 | 2708.42 MiB | 2740.80 MiB |
| Ara, 시드 2026 | 17.313초 | 2703.38 MiB | 2997.32 MiB |
| Eve, 시드 2026 | 17.782초 | 2708.42 MiB | 3014.48 MiB |

시간에는 Seed-VC 모델 로딩과 변환이 포함된다. 앞단 ACE-Step 생성, Demucs 분리, 반주 재결합, MP3 인코딩은 포함되지 않는다. 측정은 서로 다른 새 프로세스에서 수행했으며 캐시 상태가 달라 첫 결과와 나머지를 동일한 조건의 속도 차이로 해석하면 안 된다. GPU 장치 전체 메모리에는 다른 앱 사용량이 섞이므로 위 표는 PyTorch 할당량을 사용했다. RAM은 프로세스 작업 집합 표본의 최댓값이다.

분리된 보컬의 WavLM 화자 지표는 첫 시드에서 Ara 변환이 Ara 0.9124 / Eve 0.8866, Eve 변환이 Ara 0.8185 / Eve 0.9104로 목표 참조 방향을 구분했다. **이는 인식률·유사도 백분율이 아니다.** WavLM은 말소리용 모델이고 언어·음정·발성에 영향을 받으며 가창용 합격 기준이 없다. 음색 동일성, 발음, 가사 정확도, 장시간 안정성은 이 수치로 보증할 수 없다.

각 변환 보컬은 44.1kHz 모노 29.989초다. 보코더 프레임 반올림으로 약 11.4ms가 짧아 반주와 합칠 때 끝에 무음만 붙였다. 시간 늘이기나 음정 변경은 하지 않았다. 50ms를 넘는 길이 차이는 오류로 처리한다. 최종 음원 4개는 모두 48kHz 스테레오 WAV와 320kbps MP3로 저장했고 전체 디코딩, 유한 값, 비무음, 정확히 30초임을 확인했다. 피크를 제어하기 위해 혼합 전체에 공통 이득을 적용했다. Demucs 분리 잔여 반주에 원래 보컬이 일부 남을 수 있다.

현재 준비된 음색은 Ara/Eve뿐이다. 다른 페르소나를 임의로 둘 중 하나로 대체하지 않는다. Luna/Iris는 확인한 공식 공개 샘플 목록에서 찾지 못했으며 별도 정확한 참조 준비가 필요하다.

## 재현용 파일

로컬 출력 루트: `.music-runtime/persona-singing-v1/` (Git 제외).

- ACE-Step 비교: `probe-8652a301/report.json`, 각 사례의 `original.wav`, `preview.mp3`, `vocals.wav`.
- 변환 출력: `seed-ara-probe3`, `seed-eve-probe`, `seed-ara-2026`, `seed-eve-2026`의 `conversion.json`, `remix.json`, `song.wav`, `song.mp3`.
- 화자 진단: `probe-8652a301/speaker-conversion-diagnostic.json`.
- 참조: `profiles/ara`, `profiles/eve`의 불변 WAV와 SHA-256/출처 manifest.

실험 도구는 `services/music/verify_persona_singing.py`, `prepare_singing_vocals.py`, `probe_singing_conversion.py`, `remix_singing_conversion.py`, `evaluate_singing_voice.py`다. 참조 등록 도구 `singing_voice.py`는 음성을 생성하거나 다운로드하지 않는다. 참조 파일 변조, 경로형 음색 ID, 없는 음색, 유료 생성과의 혼합을 거부한다.

초기 실험 당시 `singingVoice`는 ACE-Step 참조 비교용이었으며 Seed-VC는 별도 probe였다. 아래 2026-10-09 후속 통합에서 Worker의 기본 페르소나 경로를 Seed-VC로 연결했다. 기존 참조 비교는 `ace_reference_experiment`를 명시할 때만 실행한다.

- funasr/campplus: `e4b6ede7ce16997aff4ae69fbca1f0175e2afede`.

모델 파일은 사전에 내려받은 고정 manifest 경로로만 로딩한다. 변환 중 Hugging Face offline 모드를 사용한다. Seed-VC 의존성은 별도 `seed-deps`에 설치해 기존 생성 환경의 PyTorch를 다운그레이드하지 않았다. 초기 두 변환은 누락된 `flatten_dict`, `dateutil` 의존성으로 실패했고 정상 의존성을 추가한 뒤 성공했다. 실패 기록은 보존했으며 모델을 다른 것으로 바꾸거나 검사를 건너뛰지 않았다.

실험은 유휴 Worker를 확인하고 일시 정지한 뒤 실행했으며 각 실행의 `finally`에서 자동 시작을 복원했다. 마지막 복원 후 Worker는 HTTP 200, 작업 수락 가능, 활성 작업 없음, 오류 없음이었다. 관련 단위 테스트 93개 통과. 프런트엔드는 변경하지 않았다.

## 후속 적용 조건

1. 사용자가 비교 음원에서 원래 xAI 목소리 유사성과 가창 품질을 확인한다.
2. 선택한 경로를 로컬 Worker 큐에 통합하고 실패 시 다른 목소리로 대체하지 않도록 검증한다.
3. 나머지 페르소나의 정확한 참조를 준비하고 추가 곡·음역·시드로 비교한다.
4. NAS API와 웹앱에 명시적인 실험 기능 선택을 추가하고 전체 흐름을 검증한 뒤 출시한다.

공식 참고: [xAI TTS 문서](https://docs.x.ai/developers/model-capabilities/audio/text-to-speech), [Seed-VC 원본](https://github.com/Plachtaa/seed-vc), [ACE-Step Diffusers 문서](https://huggingface.co/docs/diffusers/api/pipelines/ace_step).

## 2026-10-09 후속 통합 및 RVC 준비

사용자가 Ara/Eve 비교 음원의 차이와 xAI 참조 유사성을 청취 확인한 뒤 진행을 승인했다. Worker는 ACE-Step 생성 프로세스 종료 → CPU Demucs 보컬 분리 → Seed-VC GPU 변환 → 반주 재결합 순으로 실행한다. 전체 동안 기존 Worker GPU 큐 잠금을 유지한다. 원본 생성물과 단계별 로그를 보존하며 없는 음색을 다른 것으로 대체하지 않는다.

| 실제 Worker 작업 | 결과 | 전체 모델 처리 | 분리·변환·재결합 | 최종 음원 |
| --- | --- | ---: | ---: | --- |
| Ara `7df8518b-3c06-4306-9ee3-350389f6e6a2` | COMPLETED | 125.377초 | 92.848초 | 30초 WAV/MP3 |
| Eve `7e716ca1-751e-47e5-be52-bcceb5d72232` | COMPLETED | 236.006초 | 206.132초 | 30초 WAV/MP3 |

전체 모델 처리 시간은 ACE-Step과 변환 파이프라인 합계이며 큐 대기·최종 저장 시간을 포함한 사용자 대기시간과 다르다. 두 음원 모두 전체 디코딩, 48kHz 스테레오, 정확히 30초, 비무음·유한 PCM을 확인했다. API 비용은 0이다. 이 두 출력의 가창 품질은 별도 청취가 필요하다.

앞선 실제 큐 시도 두 번은 ACE-Step에서 네이티브 접근 위반 `0xC0000005`로 실패했다. Windows 이벤트의 오류 모듈은 PyTorch `c10.dll`이다. 독립 진단과 이후 Ara/Eve 큐 작업은 성공했지만 근본 원인을 규명하거나 완전히 해결했다고 판단하지 않는다. 실패 기록을 보존하고 faulthandler 및 네이티브 종료 코드 보고를 추가했다. 최초 변환 시도의 Windows venv 부모 프로세스 검증 오류는 상위 두 단계에서 Worker와 잠금을 확인하도록 수정했다.

NAS API에는 선택값 검증과 `personaSingingSupported` 협상, 준비된 `singingVoices` 상태를 추가했다. 웹 UI는 현재 선택한 페르소나의 음색이 실제 준비됐을 때만 무료 로컬 선택을 활성화한다. 준비된 음색은 Ara/Eve뿐이다. 유료 생성과 조합을 거부한다. NAS 업데이트와 웹앱 게시 여부는 배포 확인 후 별도로 기록한다. 기존 공개 웹앱 버전은 1.34.8이며 이번 코드 변경으로 자동 출시되지 않는다.

백엔드 98개, 프런트엔드 495개 테스트가 통과했다. typecheck/build와 개발·빌드 결과의 데스크톱/모바일 렌더 검사에서 런타임 오류·가로 넘침이 없었다. 로컬 생성 성공을 NAS 웹앱 전체 흐름 성공으로 해석하지 않는다.

RVC 공식 소스 `81eed5e8f68b6bed1789f682fe78cdd324495afc`와 격리된 의존성 환경을 준비했다. 기존 CUDA PyTorch 2.7.1을 재사용하며 오프라인 HuBERT 모델 로딩과 핵심 VC 모듈 import를 확인했다. `rvc_dataset.py`는 파일 해시 중복과 실제 유효 음성 시간을 점검하고, `rvc_voice.py`는 학습된 모델을 불변 해시로 등록한다. `rvc_runtime.py`는 등록된 모델만 쓰는 독립 변환 도구다. **학습 모델이 없으므로 실제 RVC 변환·가창을 검증하거나 UI에 활성화하지 않았다.**

사용자가 지정한 `I:/Grok/페르소나음성` 경로에는 음성이 없었다. 아라/서연 폴더를 만들었으며 각각 데이터는 0초다. 각 폴더는 한 목소리만 포함해야 한다. xAI Ara/Eve 매핑을 확인하고 충분한 실제 음성이 준비된 뒤 데이터 점검 → 학습 → 미사용 곡 청취 비교를 진행한다. 공식 RVC 문서는 잡음이 적은 최소 약 10분 음성을 권장한다. 시간 조건은 품질 보증이 아니다. DiffSinger는 음표·음소·정렬된 가창 데이터가 필요한 별도 경로로 검토했으며 설치·학습·서비스 적용은 하지 않았다.

RVC 참고: [공식 README](https://github.com/RVC-Project/Retrieval-based-Voice-Conversion-WebUI/blob/main/docs/en/README.en.md), [DiffSinger 데이터 권고](https://github.com/openvpi/DiffSinger/blob/main/docs/BestPractices.md).

NAS 후속 확인: DSM 수동 작업으로 패키지 SHA-256 검증, 기존 API 파일/compose 백업 후 API 코드 세 파일만 교체하고 서비스를 재빌드했다. Windows bridge도 새 코드로 재시작했다. 실제 NAS HTTPS `/health` 인증 요청에서 `personaSingingSupported: true`, `singingVoices: ["ara", "eve"]`를 확인했다. 보고서는 `.music-runtime/persona-singing-v1/nas-persona-health.json`이다. NAS/Grok 웹앱의 새 UI 게시와 실제 NAS 페르소나 작업 전체 생성은 아직 확인하지 않았다.

## 2026-10-10 음성 폴더 구성

사용자 요청으로 기존 로컬 참조 MP3를 `I:/Grok/페르소나음성/{페르소나}`에 복사했다. 원본은 유지하며 덮어쓰기 전 동일 해시를 확인한다. 파일별 출처 경로와 SHA-256은 루트의 `음성파일목록.json`, 디코딩 및 분량 결과는 각 폴더의 `데이터점검.json`에 저장했다. 공개 참조 외 장문 음성은 확인하지 못했고 사용자도 다른 보관 폴더가 없다고 답했다.

| 혜정 | luna | 11.352초 | 7.4초 |

Ara/Eve는 앞선 불변 프로필 출처를 확인한 참조다. 나머지 네 파일은 기본 페르소나 매핑과 파일명에 따라 분류한 후보이며 원본 출처·실제 음색 확인이 추가로 필요하다. 이 복사로 Seed-VC 지원 프로필이 늘어나지는 않는다. 모두 권장 학습 분량에 부족해 RVC 학습을 시작하지 않았다. 반복 복사, 생성 가창 출력 재학습, 유료 TTS 호출을 하지 않았으며 API 비용은 0이다. 장문 데이터 확보가 RVC의 다음 선행 조건이다.

## 2026-10-10 승인된 장문 TTS 데이터 확보

## RVC 청취 피드백 및 발음 비교

사용자가 Ara/Eve 노랫소리가 서로 비슷하고, ‘따뜻한’, ‘실어’, ‘작은’, ‘있을게’의 마지막 ‘게’에서 발음·소리가 어색하다고 보고했다. 따라서 이번 RVC 파일 생성은 기술 검증을 통과했지만 **페르소나 구분·발음 청취 품질은 미통과**로 기록한다. 서비스 기본 경로를 RVC로 바꾸지 않는다.

같은 원곡 seed 1042에서 다음 두 실험을 각각 Ara/Eve에 적용한다. 기본값과 한 변수씩 비교하며 피치를 인위적으로 바꾸어 목소리 차이를 만들지 않는다. 추가 TTS·유료 ASR 호출은 없다.

- 특징 검색 비중: index 0.75 → 0.35, protect 0.33 유지.
- 무성 구간 보호: protect 0.33 → 0.10, index 0.75 유지.

원본 RVC 소스의 `pipeline.py`에서 protect는 F0가 없는 구간의 검색 특징과 원본 특징의 비중을 조절한다. 유성 모음의 소리나 가창 원본이 잘못 발음한 단어를 자동으로 고치는 기능이 아니다. 검색 비중을 낮추면 원곡 특징이 더 남으므로 페르소나 유지와 발음 보존의 절충을 청취로 확인해야 한다. `rvc_runtime.py`에 실험용 두 인수를 추가하고 범위를 벗어난 값과 NaN을 거부한다. 기본값은 변경하지 않는다.

비교 음원은 `rvc-tune-{ara,eve}-{index035,protect010}-1042`에 별도로 보존한다. 원곡 보컬·Seed-VC·기본 RVC·새 실험 보컬을 동일한 오프라인 Qwen3-ASR로 비교하며 정답 가사는 받아쓰기 모델에 제공하지 않는다. ASR 결과는 알아들을 수 있는 가사의 보조 지표이며 음색·자음의 질감·음표 끝 왜곡을 판정할 수 없다. 원곡의 발음이 잘못되었는지와 변환에서 왜곡되었는지의 원인은 이 지표만으로 확정하지 않는다.

네 추가 변환과 아홉 보컬의 ASR 비교를 완료했다. 네 WAV·MP3 모두 정확히 30초 전체 디코딩을 통과했고, GPU Worker도 복원됐다. 기준 가사는 원곡 생성 요청의 네 줄이며 문장부호·공백을 제외한 42자를 비교한다. 결과는 `rvc-pronunciation-probes.json`, `rvc-pronunciation-asr.json`에 보존했다.

현재 비교에서 Ara 자음 보호 강화와 Eve 검색 비중 감소는 ASR 기준 개선 후보지만, Eve 자음 보호 강화는 오히려 악화됐다. 기본 RVC에서는 ‘따뜻한’과 마지막 행 등에서 추가 오인식이 나타나 사용자가 지적한 변환 왜곡을 의심할 근거가 있다. 원곡에도 ‘작은 노래가 빛나’ 등의 인식 오류가 있어 전체 문제를 RVC 하나로 단정하지 않는다. Ara 후보에도 ‘따뜻한’, ‘작은’, ‘있을게’의 오인식이 남았고 Eve 후보의 ‘작은’도 오인식했다. 발음 문제가 완전히 해결된 것은 아니다. 두 음색의 청취 구분도 재검증이 필요하므로 개선 후보를 서비스 기본값으로 적용하지 않았다.

후속 청취에서 사용자는 위 후보의 ‘따뜻한’을 제외한 나머지 발음이 개선됐다고 확인했다. 이 피드백은 개별 음색 점수가 아니라 함께 제시한 두 후보에 대한 보고로 기록한다. 다음 실험은 Ara의 index 0.75와 Eve의 index 0.35를 유지하며, 두 음색 모두 protect를 0.00으로 내려 무성 구간의 원본 특징 보존을 더 강화한다. 앞선 후보는 덮어쓰지 않으며 새 실험은 `rvc-tune-{ara,eve}-protect000-1042`와 `rvc-tt-phoneme-probes.json`에 따로 보존한다. 이 값은 무성 구간에만 작용하므로 ‘따뜻한’ 전체 발음 개선을 보장하지 않는다. 두 목소리의 구분 문제는 아직 해결 확인을 받지 못했다.

protect 0.00의 두 변환 및 로컬 ASR을 완료했다. Ara 오류는 8 → 12자로 악화됐고 ‘따뜻한’은 ‘닿지 않는’으로 인식됐다. ### Ara 100회차 격리 학습 — 2026-10-10

사용자의 다음 진행 요청에 따라 기존 40회차 Ara 체크포인트를 별도 `persona-ara-20261010-e100` 실험으로 복사하여 명목 100회차까지 재개한다. 원본 모델·등록 프로필·청취 확인된 설정은 덮어쓰지 않는다. upstream 재개 루프는 저장된 40회차부터 다시 시작하므로 100회 추가 학습이 아니다. 새 음성이나 유료 API 호출은 없으며 학습/평가 분리도 유지한다.

첫 시도는 Windows 오류 1455와 `Couldn't open shared file mapping`, `Memory allocation failure`로 중단했다. 당시 물리 RAM 여유는 약 19GB였지만 가상 메모리 여유는 약 460MiB였다. GPU 메모리 부족 오류로 분류하지 않는다. [Microsoft의 commit limit 설명](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/how-to-determine-the-appropriate-page-file-size-for-64-bit-versions-of-windows)에 따르면 commit limit에는 RAM과 페이지파일이 함께 관여하며, 물리 RAM 여유만으로 할당 가능성을 판단할 수 없다. 시스템 페이지파일과 사용자 앱은 변경하지 않았다.

재시도는 외부 `rvc_train_runtime.py` 어댑터로 DataLoader workers를 4에서 0으로 줄이고 prefetch/persistent worker 옵션을 조정했다. 모델·학습 데이터·optimizer는 동일하며 pinned upstream 소스는 수정하지 않았다. 실제 DataLoader의 전체 데이터 순서/커버리지와 옵션 원본 보존을 사전 확인했다. 각 실행은 Worker가 비어 있을 때만 중단하고 GPU 락 안에서 수행하며 finally에서 Worker를 복원한다. 첫 실패와 재시도 기록은 `pilot-history.jsonl`에 보존한다.

비교 계획은 기존 seed 1042와 2026의 보컬을 각각 사용하여 Ara index 0.75/protect 0.10을 고정하고 40/100회차 모델만 바꾸는 것이다. ASR은 정답 가사를 받지 않고 실행하며, 평가 결과는 발음 가독성의 보조 지표로만 사용한다. 음색 구분과 자연스러움은 사용자 청취 확인이 필요하다.


100회차 재시도는 완료됐다. 학습 1003.379초, 특징 추출 8.376초, 인덱스 7.161초, 전체 1021.674초다. export의 `info=100epoch`, v2와 전 가중치 finite를 확인했고 별도 `ara-e100` 프로필로 등록했다. 기존 Ara/Eve 프로필 해시도 그대로다. 첫 실패와 완료 이력은 보존했다.

### 학습 데이터 분포 진단과 낮은 키 통제 실험 — 2026-10-10

학습 회차 증가 결과가 혼재하여 기존 데이터의 단어/음높이 분포를 점검했다. 원 대본 정확 문자열 횟수는 따뜻한 1, 실어 0, 작은 33, 있을게 0이다. 활용형/발음 단위 횟수는 아니다. 실제 Ara 전처리 조각 201개를 offline Qwen으로 전부 받아쓰기했으며 정답 대본을 ASR에 제공하지 않았다. 따뜻한은 `0_87.wav`의 ‘그래도 속은 부드러웠고 따뜻한 한 조각을’에서 1개 조각, 작은은 21개 조각에서 인식했다. 실어/있을게의 정확 표기는 인식되지 않았다. ASR 누락은 음성에 해당 발음이 없었다는 확정 증거가 아니며, 겹치는 조각을 고유 횟수로 해석하지 않는다. heldout은 분석 및 학습 변경에 포함하지 않았다. 추가 API 비용 0, 점검 실행 284.362초, Worker 복원 정상이다.

기존 학습 F0와 같은 RMVPE 모델의 CPU float32 노래 F0를 비교했다.
