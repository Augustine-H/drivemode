# 보컬 생성 및 노래 인식

## 2026-10-06 반복 가사 보존 및 개선 후보 비교 — 1.28.2

반복 후렴을 압축률만으로 통째로 삭제하던 처리를 수정했다. 가사는 보존하고 오인식 가능성을 경고하며, 전체 짧은 문자 루프는 제외한다. Thai/Vietnamese 전용 모델과 전체 보컬 분리 입력의 비교에서는 일관된 정확도 개선이 없어 기본 Qwen을 유지했다. 절·후렴 번호 입력은 60초 두 생성 사례의 가사 일치 지표를 개선했지만 자동 입력 변경으로 적용하지 않는다. 실제 API의 Thai 원문 보존과 일본어 기존 정확도를 확인했다. 측정치·실패 후보·한계는 [1.28.2 검증 기록](music-validation-1282.md)에 정리했다.

## 2026-10-06 인식 후보·중국어/태국어/베트남어·보컬 연속 검증 — 1.28.1

가사 입력의 조용한 토큰 절단 방지, 입력 오류 뒤 Worker의 다음 작업 처리, 태국어 모음·성조를 보존한 경계 비교를 반영했다. 고정 모델 비교 28건, 우선 언어 분할 비교 9건, 보컬 30/60/120초 두 시드의 연속 생성 및 가사 일치 프록시 평가를 진행했다. 더 큰 Whisper로 교체하거나 짧게 분할해도 인식의 일관된 개선을 확인하지 못했고, 태국어·베트남어 가창 정확도는 아직 부족하다. 생성 설명 후보의 일부 가사 일치 개선은 전체 보컬 품질 보장이 아니다. 조건·측정·한계는 [1.28.1 검증 기록](music-validation-1281.md)에 정리했다.

## 2026-10-06 가사 직접 수정·보관 — 1.28.0

완료 또는 취소된 받아쓰기 결과에서 `가사 수정`으로 직접 편집하고 저장할 수 있다. AI 인식 원문과 사용자 수정본을 구분하며 첫 저장 시 원문도 함께 보관한다. 편집 취소는 임시 변경만 버리고, `AI 원문으로 채우기`는 편집 중인 내용만 채운다. 저장본과 원문을 각각 UTF-8 BOM TXT로 내려받는다. 수정본은 최대 60,000자이며 저장 시각 및 취소된 작업의 일부 원문 여부를 함께 기록한다.

수정 정보는 NAS 요청이 아닌 로컬 대화의 선택적 `editedLyrics` 필드에 들어간다. 기존 IndexedDB 대화 저장과 JSON 대화 백업·전체 기억 아카이브를 사용하며 저장체계의 호환 버전은 바꾸지 않는다. NAS/Worker 원문과 구간별 원문은 변경하지 않는다. NAS 결과 없이 복원해도 보관 원문·수정본 표시와 TXT 다운로드가 가능하다. 사용자 수정은 모델 학습이나 자동 인식 정확도 개선을 의미하지 않는다.

즉시 새로고침 검증에서 기존 대화 저장의 250ms 지연 때문에 완료 안내 전에 새로고침하면 수정본이 누락되는 문제를 발견했다. 수정 저장은 기존 저장 큐의 실제 기록 완료를 기다린 뒤 완료를 알리고, 저장 실패 시 편집 상태와 오류 안내를 유지하도록 수정했다. 영어 개발 화면과 일본어 배포용 화면에서 저장 완료 직후 새로고침으로 수정본 및 원문 보존을 확인했다. 초기화 후 편집 취소도 저장본을 유지했다.

실제 내려받은 영어 원문·수정본 TXT의 내용 및 BOM `EF-BB-BF` 일치를 확인했고 일본어 TXT의 UTF-8 내용을 확인했다. 브라우저의 download 이벤트는 시간 초과했지만 다운로드 폴더의 실제 파일을 검증했다. 중립적인 검증용 대화 JSON을 별도 검증 주소에서 복원해 수정본·부분 원문 경고·보관 원문을 확인하고 새로고침 후 유지를 검증했다. 전체 기억 아카이브 직렬화/복원과 잘못된 수정 메타데이터 거부를 포함한 음악 모델 테스트 9개가 통과했다.

개발·배포용 화면을 데스크톱 1280×900 및 모바일 390×844에서 시각 확인했다. 편집창·버튼·텍스트가 표시되고 페이지 가로 넘침이나 콘솔 오류는 없었다. 모바일 페르소나 목록의 기존 내부 가로 스크롤은 유지한다. 타입 검사와 빌드 통과, 변경 파일 lint 오류 0개(기존 `turns` 의존성 경고 4개). 검증 음원·전체 정답·다운로드 및 화면 캡처는 Git에 포함하지 않는다.

## 2026-10-06 일반 음악 문맥 힌트 검증

설치된 Transformers 5.18.0의 Qwen3-ASR processor에서 `apply_transcription_request(..., prompt=...)`의 문맥/어휘 힌트 지원을 확인했다. 기존 고정 모델·BF16/SDPA/greedy·언어 지정·30초/3초 겹침을 유지하고 무힌트 기준과 일반 음악 문맥 2종을 같은 원본 음원으로 비교했다. 문맥은 “노래의 원어 가창을 받아쓰기” 및 “반복을 보존하고 들리는 단어만 받아쓰기”라는 일반 지시이며, 정답 단어/가사/곡 제목은 넣지 않았다. 특정 어휘를 알려 주는 hotword 효과를 검증한 실험으로 주장하지 않는다.

일본어 전체 104자 CER는 3조건 모두 5/104 (4.81%), 고정 동등 표기 후 2/104 (1.92%). 한국어 공통 첫 절 61자 CER는 모두 4/61 (6.56%). 영어 첫 25초 21단어 WER는 모두 1/21 (4.76%)였다. 이 평가 범위에서 일반 음악 문맥으로 오류 감소를 확인하지 못해 제품에 기본 프롬프트를 추가하지 않았다. 한국어 뒤쪽의 추가 변화 여부를 첫 절 점수와 혼동하지 않는다.

모델을 한 번 로드한 네이티브 비교 9회이며 실제 30초 창 처리 횟수는 15회다. GPU Worker가 인증 상태상 유휴인지 확인한 뒤 잠시 중단하고 동일 GPU 파일 잠금으로 직렬 실행했으며 finally에서 Worker를 복구했다. 준비용 PowerShell 프로세스 확인식에서 정규식 이스케이프 오류가 발생해 오류 시 즉시 중단하도록 하고 정확한 소스 경로의 literal 확인으로 수정했다. 해당 포트의 인증된 유휴 Worker를 대상으로 했으며 다른 앱 프로세스는 중단하지 않았다. 종료 후 브리지 IDLE/workerReady=true를 확인했다.

모델 로딩 3.767초, 이후 warm inference 합계(각 조건의 1~2창)는 일본어 5.795/4.743/4.586초, 한국어 4.072/5.335/4.394초, 영어 1.421/1.531/1.443초였다. 최초 조건의 워밍업 차이가 있으므로 속도 개선으로 일반화하지 않는다. 최대 할당 VRAM은 4045.13~4074.77 MiB. 원본/결과/평가는 gitignored `.music-runtime/qwen-asr/context-hints/`에 보관했다. 앱/NAS 설정과 버전 1.27.0은 유지했다. 구체적인 사용자 어휘 힌트나 노래 맞춤 학습의 효과는 아직 확인하지 않았다.

## 2026-10-06 보컬 쉼 경계 분할 후보 검증

같은 일본어/한국어/영어 원본 녹음으로 보컬 음량이 낮은 구간에서 나누는 후보를 검증했다. 기존 로컬 HDEMUCS_HIGH_MUSDB_PLUS 분리본은 경계 분석에만 사용하고 Qwen에는 원본 PCM을 넣었다. 모델·언어·BF16/SDPA/greedy 설정은 유지했으며 기준 가사와 곡 제목을 경계 탐색/추론에 사용하지 않았다. 분리본의 낮은 음량은 쉼의 추정값이며 반주 누출/작은 보컬을 실제 무보컬 구간으로 확정하지 않는다.

40ms 보컬 RMS의 하위 20백분위 +3dB, 240ms 이상 낮은 음량 구간을 사용했다. 고정 목표(긴 파일 24초, 영어 25초 샘플은 18초)의 ±5초 내에서 가까운 쉼/긴 쉼을 각각 비교했다. 경계 중앙의 ±100ms로 원본 창을 나누고 두 원문을 줄바꿈으로 보존했다. 중복 삭제로 결과를 보정하지 않았다. 한국어 앞뒤 무음으로 전역 기준이 -65dB까지 낮아져 목표 부근의 후보가 없어 해당 분할은 거부했다. 이후 목표 ±5초의 국소 기준(p20+3dB, p75-10dB 이하)을 모든 언어에 동일하게 비교해 한국어 22.16초 후보를 찾았다. 임의의 고정 시점으로 대체하지 않았다.

| 평가 범위 | 기존 오류 | 가까운 쉼 / 국소 쉼 | 긴 쉼 |
|---|---:|---:|---:|
| 일본어 35.968초 전체 104자 | 5/104 (4.81%) | 24.48초: 7/104 (6.73%) | 26.58초: 5/104 (4.81%) |
| 한국어 공통 첫 절 61자 | 4/61 (6.56%) | 국소 22.16초: 4/61 (6.56%) | 전역 기준 후보 없음 |
| 영어 첫 25초 21단어 | 1/21 (4.76%) | 19.04초: 1/21 (4.76%) | 동일 경계, 1/21 (4.76%) |

일본어 동등 표기 정규화 후에도 기존 2/104 대비 가까운 쉼 4/104, 긴 쉼 2/104였다. `人生柄`→`人生から` 오류는 남았다. 한국어는 이전 임의 24초 분할의 짧은 구절 중복을 피했지만 기존 제품의 첫 절 정확도를 개선하지 못했다. 한국어 뒤쪽 구절의 일부 표현도 달라져 첫 절 수치를 파일 전체 개선으로 주장하지 않는다. 영어의 `auld`→`old` 단어 오류도 남았다.

인증 Worker의 실제 ASR 작업 10개가 모두 완료했고 저장 파일에서 입력 오디오/임시 요청 파일 제거를 확인했다. 국소 분석에서 동일 원본·동일 경계로 나온 일본어/영어 창은 완료 결과를 재사용했으며 추가 추론으로 세지 않았다. 44.1k→16k 경계 분석용 분리본이 원본보다 1샘플 길어지는 재표본화 반올림을 확인했다. 분석용 분리본의 끝 1샘플만 제외하고 원본 추론 음원은 변경하지 않았다. 다른 길이 불일치는 허용하지 않았다.

두 창의 모델 로딩 포함 시간 합계는 일본어 가까운 쉼 20.078초/긴 쉼 20.051초, 한국어 국소 쉼 20.278초, 영어 가까운 쉼 16.917초/동일 긴 쉼 반복 17.026초였다. 경계 분석용 모델 분리 시간은 이 합계에 포함하지 않았다. 후보·원문 차이·경계 정보·측정은 gitignored `.music-runtime/qwen-asr/rest-split{,-longest,-local}/`에 보관했다. 이 3개 녹음에서 오류 감소를 확인하지 못해 제품의 분할/인식 설정과 버전 1.27.0을 유지했다. 보컬 쉼 분할의 일반적 효과를 부정하는 결과는 아니지만 자동 적용의 근거로 사용하지 않는다.

## 2026-10-06 문맥 범위 변경 재인식 후보 검증

기존 Qwen BF16/SDPA/greedy와 언어 지정 설정을 유지하고, 같은 실제 녹음에서 분할 위치와 앞뒤 문맥만 변경했다. 일본어 35.968초는 18/24/27초 위치에서 각각 나누고 3초씩 겹쳤다. 한국어 35.371초는 24초 위치, 영어 첫 25초는 18초 위치를 비교했다. 후보 5개 × 2창의 인증 Worker 작업 10개 모두 완료했고 실제 저장 파일에서 입력 오디오 및 임시 요청 파일 삭제를 확인했다. 정답과 곡 제목은 모델 입력에 넣지 않았다. 후보별 기존/재인식의 달라진 문자와 시간·자원 측정은 gitignored `.music-runtime/qwen-asr/context-retry/`에 보관했다.

## 2026-10-06 전체 파일 가사 받아쓰기 구현 · NAS 통합 검증 · 1.27.0

## 2026-10-06 일본어 개선 후보 비교 및 채택 보류

보컬 분리, 동일 Qwen 모델의 beam 탐색, 기존 로컬 Whisper를 실제 음악에 비교했다. **제품의 기본 인식 설정으로 채택할 만큼 일관된 일본어 개선은 확인하지 못했다.** 원본→분리본 Worker 14개 작업, 실황 Qwen Worker 1개 작업, 네이티브 Qwen 후보 탐색 16회, Whisper 6회(음악 4회/연주곡 1회/침묵 1회)를 수행했다. 보컬 분리 자체는 7회이며 모두 완료했다. 인식 실행은 총 37회다. 실제 모델 실행 실패는 없었지만 가사 품질 실패는 있었다. 모델이나 서비스의 자동 대체를 제품에 추가하지 않았다.

정답은 이전 검증의 공개/사용자 기준문을 그대로 비교에만 사용했다. 일본어 첫 절은 고정 한자→가나 대응으로 비교할 수 있지만, 뒷절의 실제 가창 변형을 청취로 확정하지 못했다. 따라서 뒷절 전체 CER은 확정된 정확도 수치로 사용하지 않는다. 한자/가나 정규화는 음소 평가가 아니며, 기존 측정의 한계를 유지한다. 잘못된 한자를 기준 가사로 자동 교정하거나 정답 가사를 모델 입력에 넣지 않았다.

### 1. 보컬 분리

기존 [torchaudio Hybrid Demucs](https://docs.pytorch.org/audio/2.7.0/tutorials/hybrid_demucs_tutorial.html)의 `HDEMUCS_HIGH_MUSDB_PLUS`를 사용했다. 로컬 `hdemucs_high_trained.pt`의 SHA256 `a004b2790d73ffeaa535db458a1a79b539dfdbafbccc31f275d07e632ebd7816`를 확인하고 직접 `weights_only=True`로 로드했다. 다운로드 경로를 호출하지 않았다. 제품이 받는 16 kHz mono PCM을 44.1 kHz 2채널로 변환하여 분리한 뒤 다시 16 kHz mono로 만들었으며, gain boost/peak normalization은 하지 않았다. 8초 블록/1초 overlap을 유지했다. 각 원본과 분리본을 같은 언어 지정·Qwen BF16/SDPA/greedy 조건의 인증 Worker API에서 순차 실행했다.

| 비교 구간 | 원본 | 분리 후 | 판단 |
|---|---:|---:|---|
| 일본어 첫 절 / 고정 가나 CER | 2/38 = 5.26% | 2/38 = 5.26% | 출력 동일 |
| 스페인어 첫 후렴 / WER | 0/17 = 0% | 0/17 = 0% | 유지 |
| 영어 25초 / WER | 1/21 = 4.76% | 1/21 = 4.76% | 유지 |
| 중국어 전체 두 구간 / CER | 2/84 = 2.38% | 33/84 = 39.29% | 큰 회귀 |
| 한국어 공통 첫 절 / CER | 4/61 = 6.56% | 채점 경계 확인 불가 | 분리본에서 문장/끝구절이 크게 달라 확정 CER을 계산하지 않음 |

일본어 뒷절도 원본·분리본의 결과가 동일했다. 분리 자체 로딩+처리는 1.660~1.872초, 최대 할당 VRAM 692.19 MiB. 이후 ASR 모델 단계는 구간별 9.311~12.106초(로딩 포함)였다. 자원 수치를 합산해 동시 점유량으로 해석하지 않는다. 분리와 인식을 순차 실행했다. 분리본은 모든 언어에 유리한 처리가 아니므로 기본 경로에 적용하지 않는다.

### 2. Qwen 후보 탐색과 문맥 길이

같은 고정 Qwen 리비전을 한 번 로드해 `num_beams=1/3`, `do_sample=False`, max_new_tokens=512를 비교했다. 5개 언어와 일본어 뒷절/30초 연속 문맥을 포함한 8개 입력 × 2개 설정이다. 모델 로딩은 별도로 측정했고 각 행 시간은 warm inference이므로 Worker의 로딩 포함 시간과 직접 비교하지 않는다.

- 일본어 첫 절의 고정 가나 CER: 2/38 → 7/38(5.26% → 18.42%). 후보를 늘리자 새 단어/누락 오류가 발생했다.
- 일본어 뒷절의 핵심 단어 오류가 해결되지 않았다. 30초 연속 문맥에서도 해결되지 않았고 beam3에서 이름에 추가 글자가 생겼다.
- 스페인어 WER 0/17, 영어 WER 1/21, 한국어 공통 절 CER 4/61은 유지됐다.
- 중국어 전체는 CER 2/84 → 1/84로 소폭 줄었지만 마지막 반복 글자 삽입이 남았다. 한 녹음에서의 이득이며 일본어 회귀를 정당화하지 않는다. 공통 설정을 beam3로 바꾸지 않았다.

### 3. Whisper 후보의 일본어 추가 검증

이미 설치된 `openai/whisper-large-v3-turbo`, 리비전 `41f01f3fe87f28c78e2fbf8b568835947dd65ed9`를 다운로드 없이 FP32 CUDA, 일본어 지정, beam5, task=transcribe 조건으로 실행했다. [Momotarô-san — Kaihsu Tai, CC BY-SA 4.0](https://commons.wikimedia.org/wiki/File:Momotar%C3%B4-san.ogg)의 첫 절은 고정 가나 CER 0/38이었다. 뒷절에서는 올바른 기준 한자를 복원하지 못했으며, 한 곡의 첫 절 이득만으로 교체하지 않았다.

추가 [Hakonehachiri 실황 — clenty yt, CC BY 3.0](https://commons.wikimedia.org/wiki/File:Hakonehachiri_-_japanese_song.ogg)은 피아노 반주를 동반한 사람의 가창 녹음이다. 첫 30초를 동일 16 kHz mono 입력으로 만들고, [공개 도메인 가사](https://ja.wikisource.org/wiki/箱根八里)의 처음 두 행을 사전 기준으로 고정했다. Whisper는 가사 대신 편곡 문구를 대량 반복하여 기존 `checked_lyrics`가 빈 결과/경고로 제외했다. Qwen 역시 기준 가사와 크게 다른 출력이어서 신뢰할 만한 받아쓰기가 아니었다. 두 모델 모두 비교 행의 경계를 맞출 수 없어 이 실황에 임의의 CER 점수를 만들지 않았다.

Whisper 직접 호출의 연주곡은 음악 표지 문구를, 침묵은 감사 문구를 반환했다. 이 실험은 제품의 RMS 검사 밖에서 모델을 직접 호출한 음성 부재 대조군이다. 제품의 RMS guard가 실제 침묵을 모델에 보내지 않는 기존 동작을 유지한다. 연주곡이나 불명확한 보컬에 대한 잘못된 문장 생성 가능성은 여전히 남는다. 표기상 첫 절 개선이 있었어도 실황의 반복 실패 때문에 일본어를 Whisper로 자동 전환하지 않는다.

### 검증 자료 및 운영 상태

`.music-runtime/qwen-asr/separation-comparison/`, `decoding-comparison/`, `whisper-japanese-comparison/`, `whisper-japanese-live/`, `japanese-live/`에 입력 해시/설정/시간/출력/평가/실패 양상을 보관했다. 공개 음원의 변환본과 사용자 한국어 가사를 제품/저장소에 포함하지 않는다. 한국어 원문은 비공개 런타임 자료에만 있다. 15개 완료 Worker 작업의 실제 `job.json`에서 `audioBase64` 제거, `vocal-request.json` 삭제를 재확인했다. 네이티브 비교는 로컬 전용이며 외부 ASR 전송이 없었다.

제품 소스·API 계약·배포·버전·GitHub는 변경하지 않았다. 실험 설정을 릴리스하지 않으므로 기존 dev/preview 및 Worker를 유지했다. 문서 diff 확인과 측정 JSON의 완료 상태/건수/입력 정리/비교 기준을 검증했다. 다음 실제 개선에는 청취로 확정한 일본어 가창 정답과 여러 현대 곡의 보컬/반주 조건을 갖춘 평가셋이 필요하다. 기준 가사로 결과를 덮어써 성능을 높여 보이는 방식은 사용하지 않는다.

## 2026-10-06 일본어·스페인어·중국어 실제 노래 추가 검증

스페인어 두 번째 후렴은 공개 첫 후렴 문구와 반복 구성이 달랐다. 두 번의 동일 후렴으로 가정하면 WER 23.53%지만, 실제 변형·반복을 검증하지 않은 기준이므로 정확도 표에서 제외했다. 첫 후렴의 0%를 전체 녹음으로 확대하지 않는다. 중국어는 두 모드 모두 `我们`→`中国` 두 글자 오류였고 나머지 공식 가사는 일치했다. 자동 감지가 이 세 음원의 언어 지정 결과보다 나은 점수를 내지 않았다.

언어당 한 녹음이며 일본어·스페인어 정량 평가는 첫 절/후렴만이다. 현대 팝, 다국어 혼합, 휴대폰 스피커→마이크 재녹음 성능을 대표하지 않는다. 원어 받아쓰기 경로는 동작하지만 일본어 의미 오류가 남아 있다. 알려진 곡의 언어를 직접 선택하는 기존 안내를 유지한다.

자료 확보 중 Carnegie Hall 페이지는 HTTP 403이어서 테스트 입력으로 사용하지 않았다. 보컬 합성 자료와 반주만 있는 자료도 선정에서 제외했다. 중국어는 다운로드 가능한 공식 합창 녹음을 사용했다. PDF 텍스트 추출은 악보 배치와 일부 문자를 정확히 복원하지 못해 Poppler 렌더링으로 기준문을 확인했다. 모델 추론 실패나 인식 서비스 대체는 없었다.

## 2026-10-06 외국어 가사 지원

요청의 `transcriptionLanguage`를 UI → NAS → Windows Worker → 오프라인 Qwen으로 전달한다. 생략한 기존 요청은 한국어를 유지하고, `auto`만 모델 언어 힌트를 생략한다. 영어·일본어 등 [공식 모델의 30개 언어](https://huggingface.co/Qwen/Qwen3-ASR-1.7B-hf)를 지원하며 임의 언어 코드나 보컬 생성/제목 검색 전용 요청의 언어 필드는 거절한다. 원어 받아쓰기이며 번역 기능을 추가하지 않는다. `transcriptionLanguage: auto`는 선택한 모드를 뜻하며 감지 결과를 보장하는 언어 태그가 아니다. 짧은/혼합 언어 음악에는 직접 선택을 권장한다.

NAS `/health`의 `transcriptionLanguages`로 새 계약 지원을 확인한다. 구형 NAS에서는 한국어 요청을 기존 형식으로 전송하고 외국어 요청은 업데이트 안내와 함께 비활성화한다. 재시도 접수 키에 언어를 포함하여 같은 샘플을 다른 언어로 요청할 때 이전 접수 번호를 재사용하지 않는다. 언어 메타데이터는 작업 복원에서 유지하지만 오디오와 연결 키는 백업에 넣지 않는다.

RTX 4070 Ti의 실제 Worker 인증 API로 검증했다. [Frank C. Stanley의 Auld Lang Syne (1910)](https://commons.wikimedia.org/wiki/File:Auld_Lang_Syne.ogg)의 13~38초 보컬을 16 kHz mono PCM으로 변환했다. 공개 도메인 음원이며 제품에 포함하지 않는다. 영어 지정/자동 감지 모두 원어 가사를 반환했다. [영어 자막](https://commons.wikimedia.org/wiki/TimedText:Auld_Lang_Syne.ogg.en.srt)을 추론 입력으로 사용하지 않고 결과 비교에만 사용했다. 공백·문장부호·대소문자 정규화 후 21개 단어 중 1개(`auld`→`old`) 오류, WER 4.76%였다. 한 곡/한 구간의 결과이며 외국어 노래 전체 성능을 의미하지 않는다.

말소리 두 건은 언어 전달 및 원문 출력 검증으로, 노래 정확도 근거로 사용하지 않는다. 이 최초 검증 시점에는 일본어 등 나머지 언어의 실제 보컬 정확도를 측정하지 않았으며, 이후 추가 검증 결과는 문서 상단에 기록한다. 완료한 네 Worker 작업의 임시 요청 파일과 job.json 입력 오디오 제거를 확인했다. 테스트용 공개 샘플과 측정 결과는 무시된 `.music-runtime/qwen-asr/foreign/`에만 보관한다. Python 50개 및 음악 모델 TypeScript 6개 테스트, build/typecheck를 통과했다.

검증 도구의 초기 실패: Wikimedia 요청은 기본 User-Agent로 HTTP 403을 반환하여 프로젝트를 명시하는 User-Agent를 사용했다. 변환 도구에 scipy가 없어 FFmpeg PCM 변환을 사용했다. 모델·인식 서비스 대체는 없었다.

NAS/Worker 요청과 결과의 언어가 `en`이고 대화 카드에 영어 가사가 표시됐다. 모델 단계 11.105초, 최대 할당 VRAM 4038.52 MiB, 최대 자식 프로세스 RAM 4401.52 MiB. 재접속 대기를 포함한 접수→완료 39.339초이므로 정상 상태의 고정 왕복 시간으로 해석하지 않는다. 원본 입력은 NAS 공개 요청 및 완료 Worker job.json에서 제외되고 자식 임시 요청 파일이 제거됐음을 확인했다. 최종 코드의 PC/모바일 개발·빌드 화면, 언어 선택 및 구형 API 차단 동작, 콘솔 오류 없음과 변경 파일 lint를 확인했다. 버전은 1.26.1이며 추가 GitHub 업로드는 수행하지 않았다.

## 사용자 기능

- 설정 → 음악 생성 · NAS 연결 → 보컬 노래 만들기: 곡 분위기, 직접 쓴 한국어 가사, 10~120초 길이를 입력한다. 실제 ACE-Step 음악 모델이 보컬과 반주를 함께 생성한다. TTS를 노래 생성으로 대신하지 않는다.
- 채팅: `피아노 노래 30초 불러줘. 가사: [Verse] ...`처럼 가사를 명시한다. 가사가 없는 요청은 입력 방법을 안내한다.
- 노래 인식: 파일의 처음 30초 또는 사용자가 직접 시작한 최대 30초 마이크 녹음을 16 kHz mono PCM WAV로 변환하고 개인 NAS → Windows Worker로 전달한다. 파일은 최대 32 MB이며 사용자가 선택한 작업만 실행한다. 샘플을 미리 재생할 수 있고 ‘선택한 노래 인식’을 누르기 전에는 전송하지 않는다. 설정을 닫으면 마이크 입력을 중단한다.
- 제목·가수 찾기: 별도 동의 후 ShazamIO가 로컬에서 만든 오디오 지문을 Shazam으로 전송한다. 오디오 샘플 자체는 Shazam에 보내지 않는다. 비공식 API이며 서비스 중단·검색 실패가 가능하다. 일치가 없으면 제목을 추측하지 않는다.
- 가사 받아쓰기: Qwen3-ASR-1.7B-hf를 BF16 로컬 CUDA로 실행한다. ‘가사 언어’에서 한국어(기본값), 영어·일본어 등 모델이 지원하는 30개 언어 또는 자동 감지를 선택한다. 선택한 최대 30초 구간의 원어 받아쓰기이며, 반주·발음·보컬 품질에 따라 오인식이 발생한다. 반복 문장 이상 출력은 제외하며 보컬 분리는 기본 처리에 적용하지 않는다.
- 기존 Audio Awareness를 켠 사용자의 실시간 AcoustID 인식 경로는 유지한다. 새 파일 인식은 별도의 설정 항목을 사용한다.

## 실행 및 보안

추가 보컬 라이브러리는 `.music-runtime/vocal-deps`에서 별도 자식 프로세스가 사용하며, Qwen은 네이티브 Transformers 5.18.0에서 실행한다. 하나의 Windows 대기열과 GPU 잠금으로 연주곡·보컬·인식을 순차 실행하고, 보컬/가사 인식 실행 전에 기존 연주곡 모델의 VRAM을 해제한다. ACE-Step은 BF16 + 모델 CPU offload + VAE tiling을 사용한다.

모델 리비전은 `services/music/vocal_models.py` 및 `services/music/qwen_lyrics.py`에 고정되어 있다. `prepare_vocal_models.py`는 명시적 설치 단계에서만 파일을 다운로드하고, 실행 중에는 `local_files_only=True`를 사용한다. HF 인증은 기존 Windows DPAPI를 사용하며 토큰을 소스나 인자로 저장하지 않는다. 모델이 준비되지 않은 Worker 요청은 503 `MODEL_NOT_PREPARED`로 거절한다.

NAS 인증/CORS/Tailscale 경계는 기존과 동일하다. WAV/MP3는 기존 해시·전체 디코딩·길이 검사를 통과한 후 보관한다. 인식 작업은 음원 산출물 없이 구조화된 인식 결과로 완료한다. API 조회와 대화 백업에 입력 샘플을 포함하지 않는다. 완료·실패·취소 시 요청의 샘플 필드를 제거하고, 자식 프로세스의 임시 요청 파일도 제거한다. SQLite/파일 시스템의 과거 페이지에 대한 보안 삭제를 보장하는 기능은 아니다.

## 2026-10-05 로컬 검증

RTX 4070 Ti, CUDA 12.6, torch 2.7.1. 수치는 API 전체 왕복과 MP3 인코딩을 제외한 모델 단계 기준이다. RAM은 자식 프로세스 working set 샘플 최댓값이며 전체 시스템 RAM이 아니다.

| 보컬 길이 | 로딩 | 생성 | 최대 할당 VRAM | 최대 프로세스 RAM |
|---|---:|---:|---:|---:|
| 30초 | 6.488초 | 15.216초 | 8091.67 MiB | 12394.21 MiB |
| 60초 | 6.018초 | 13.135초 | 8244.27 MiB | 12068.90 MiB |
| 120초 | 6.419초 | 15.018초 | 8782.34 MiB | 12440.44 MiB |

각 길이의 48 kHz stereo WAV와 MP3 320 kbps를 실제 생성하고 전체 디코딩 및 길이를 확인했다. 30초 출력은 8,640,044-byte WAV이며 SHA256 `19b0236b631de06defec61419ed0a22ae7edec340b4af5adde265dd8a015f199`이다. 생성된 한국어 보컬을 Whisper가 네 줄로 받아썼으나 `꿈을`→`거물`, `햇살`→`뱃살` 등의 오류가 있어 정확한 가사 복원을 보장하지 않는다. 해당 받아쓰기 모델 단계는 6.321초, 최대 할당 VRAM 1164.10 MiB였다.

한국어 합성 **말소리** 기준 테스트도 6.925초에 완료했다. 이 음성 테스트는 노래 생성 성능의 증거로 사용하지 않는다. 연주곡에서 발생한 반복 문자 오인식은 필터 추가 후 빈 받아쓰기와 경고로 처리했다.

제목 인식 검증은 [Monkeys Spinning Monkeys — Kevin MacLeod](https://commons.wikimedia.org/wiki/File:Monkeys_Spinning_Monkeys_(ISRC_USUAN1400011).mp3), [CC BY 3.0](https://creativecommons.org/licenses/by/3.0/) 음원의 첫 20초를 mono 16 kHz로 변환해 사용했다. Shazam은 제목 `Monkeys Spinning Monkeys`, 아티스트 `Kevin MacLeod & Kevin`을 반환했다(서비스 메타데이터 그대로 표시). 모델 단계 0.744초. 직접 생성한 연주곡은 1.799초에 일치 없음으로 처리했다. 테스트 음원은 제품 소스에 포함하지 않는다.

초기 실패 기록: Whisper는 `temperature=None`의 Transformers 비교 오류로 실패해 `temperature=0.0`을 명시했다. ACE-Step 첫 로딩은 다운로드 필터에서 제외된 `tokenizer/chat_template.jinja` 때문에 실패했으며, 같은 공식 리비전의 파일을 추가하고 오프라인 재검증했다. 다른 모델이나 유료 서비스로 자동 대체하지 않았다.

로컬 검증 자료는 `.music-runtime/vocal-verification` 및 Worker의 해당 `job.json`/`vocal-result.json`에 보관한다. NAS가 새 작업 유형을 지원한다고 응답하기 전에는 새 생성·인식 버튼을 비활성화하며 채팅 보컬 요청도 안내만 표시한다. 아래 NAS 검증까지 완료했다.

보컬 폼은 기존 대화 작업 카드에 접수 식별자를 먼저 보관한 후 제출한다. 인식 파일의 POST 결과가 네트워크 오류로 불분명하면 샘플/옵션 해시별 접수 식별자만 sessionStorage에 남긴다. 같은 파일을 재선택해 다시 누르면 같은 식별자를 재사용하며, 접수 성공 응답 후 해당 식별자를 제거한다. 샘플 본문이나 연결 키는 sessionStorage에 저장하지 않는다.

Python 테스트 36개, Node 테스트 11개, typecheck/build 및 신규 파일 lint가 통과했다. 개발 화면과 최신 프로덕션 빌드 모두 1280×720 및 390×845에서 내용 표시·가로 넘침·콘솔 오류를 확인했다. 기존 NAS의 지원 정보가 없을 때, 유효한 가사/파일/동의를 입력해도 새 요청 버튼이 비활성화되는 것을 확인했다. 생성된 30초 MP3는 브라우저에서 duration=30, currentTime=7.684, readyState=4, error=null로 실제 재생했다.

보컬 테스트 후 기존 Stable Audio로 5초 연주곡을 새로 생성하고 WAV/MP3 검증을 통과해 모델 전환 회귀를 확인했다. 최초 출시 검증에서는 실제 마이크 권한 허용/녹음을 포함하지 않았다. 이후 사용자가 요청한 실제 마이크 검증 결과는 아래에 기록한다.

## NAS 적용 및 앱 통합 검증

DSM 로그인 복구 후 전용 프로젝트에 `voice-grok-music-service:vocals-v1`(이미지 `fb87fb77100f`)을 빌드해 적용했다. 기존 토큰·데이터·loopback 포트·Tailscale/CORS 경계를 유지했다. 공용 compose의 localhost 기본값이 운영 Tailscale 호스트를 거절하는 400 오류를 발견해, 배포용 compose에 기존 승인된 개인 NAS 호스트를 복구했다. 개인 주소는 저장소의 공용 compose에 하드코딩하지 않는다. `/health`의 `supportedTasks`는 instrumental/song/recognition이며 Worker는 READY로 복구했다.

보컬 WAV/MP3를 인증된 NAS API에서 내려받아 Worker의 크기 및 SHA256과 일치함을 확인했다. WAV SHA256은 `3f0a82022e5f315e9bf8c72baee0524f56d3f527f7aea83007edc4de58570e1b`, MP3는 `9443382919f9e0dc10049632b685930a4450fad8f75b356100235984e0d5594d`이다. 앱 MP3 재생은 duration=30, currentTime=25.243, paused=false, readyState=4, error=null로 확인했고, WAV 앱 저장 성공 안내도 확인했다. 다운로드 버튼은 무결성 확인 후 다운로드 요청을 완료했으나 자동화의 다운로드 이벤트 수신은 타임아웃해 브라우저 다운로드 파일 경로까지는 검증하지 않았다.

인식 작업의 공개 API 및 완료된 Worker job.json에 입력 audioBase64가 없고 자식 요청 파일도 남지 않는 것을 확인했다. 보컬 음원의 라이브러리 메타데이터는 ACE-Step으로 저장하도록 수정했다. 최종 build/typecheck가 통과했고, 개발 및 최신 프로덕션 PC/모바일 화면에서 실제 내용과 깨끗한 콘솔을 확인했다. 테스트 음원과 결과는 `.music-runtime/vocal-verification`에만 보관한다.

## 실제 마이크 검증 — 2026-10-05

1.26.0 개발 앱에서 사용자가 브라우저 마이크 권한을 허용한 뒤 실제 MediaRecorder 녹음을 시작했다. 30초 자동 종료 후 `마이크-노래-샘플`이 생성됐으며, 미리 듣기에서 duration=29.879275초, readyState=4, paused=false, error=null을 확인했다. 합성 입력이나 파일 업로드로 마이크를 대체하지 않았다.

가사 받아쓰기만 선택해 NAS 작업 `58f00a07-8644-4d72-a997-b6ff977b9558`을 접수했다. Windows 브리지가 기존 상태 파일 교체의 WinError 5 접근 거부로 중단돼 대기했으며, 기존 autostart 도구로 중단된 브리지만 다시 시작했다. Worker는 유지하고 재접수 없이 원래 작업을 완료했다. Worker 작업 `e277d071-c5d8-47e3-a129-517c4630a30e`의 공개 요청에 audioBase64가 남지 않음을 확인했다.

첫 녹음 결과는 받아쓰기 없음, 경고는 ‘음성이 없거나 소리가 너무 작습니다’였다. 모델 단계 0.070초, 자식 프로세스 RAM 441.73 MiB, CUDA 할당 0 MiB로 무음 검사에서 종료됐다. 따라서 실제 녹음·미리 재생·NAS 전달·무음 처리 경로는 통과했지만, 이 샘플로 실제 발화의 Whisper 받아쓰기 정확도나 노래 제목 인식 성공을 주장하지 않는다. 지문 외부 전송은 선택하지 않았다. 비공개 결과는 `.music-runtime/microphone-verification`에 보관한다.

## turbo Worker 적용 및 실제 앱 검증 — 2026-10-06

후속 적용 요청에 따라 `vocal_models.py`의 기본 받아쓰기 모델을 비교에서 검증한 turbo 고정 버전으로 변경했다. 캐시 준비 여부와 보컬 모델 준비를 확인하고, 진행·대기 작업이 없는 Worker만 재시작했다. 첫 실제 M4A 요청은 NAS `86615a37-e974-4cfe-82aa-cd898fd1f918`, Worker `8b187905-0daa-4242-821b-735bbe729fb4`에서 `Input type (float) and bias type (struct c10::Half) should be the same`으로 실패했다. turbo 가중치의 기본 로딩 자료형이 float16인 반면 입력은 float32여서 발생했다. 비교 실험과 일치하도록 모델 로딩에 `dtype=torch.float32`를 명시하고 입력도 `model.dtype`으로 맞췄다. 실패 기록을 보존하고 정상 유휴 상태를 확인한 뒤 Worker를 복구했다. 수정 후 Python 회귀 검사 39개가 통과했다.

## M4A 반복 출력 진단 및 수정 — 2026-10-06

실제 앱이 새 녹음 M4A에서 만든 WAV를 일시 확보해 동일한 좌우 평균 FFmpeg 변환과 비교했다. 둘 다 480000 frames이며 앱 RMS -14.85065 dBFS, FFmpeg 평균 RMS -14.85085 dBFS, 파형 상관계수 0.999990이었다. 브라우저 PCM float32 바이트 SHA256은 `9084dfe2c4185f866a1b6ad23c08727c75099546d21e8a056f181e3d75c085da`이다. 기존 비교 WAV는 RMS -11.85606 dBFS, peak 0 dBFS로 음량과 일부 클리핑이 달랐다. 이번 측정은 M4A 변환 손상이 주원인이라는 가설을 지지하지 않는다.

같은 모델·같은 파형으로 디코딩만 바꿨다. 기존 greedy 디코딩은 브라우저 입력과 FFmpeg 평균 입력 모두 440 tokens까지 같은 문장을 반복했고 후처리 압축률 31.286으로 제외됐다. 브라우저 입력을 sqrt(2)배 증폭·클리핑한 경우도 반복됐다. 반면 원래 브라우저 입력에 num_beams=5를 적용하면 74 tokens, 압축률 1.297로 실제 가사 형태의 문장을 반환했다. 따라서 이 샘플의 실패는 greedy 디코딩의 반복 경로로 재현됐고 beam search로 해소됐다. 모든 음원에서 발생하는 근본적인 모델 오류 원인까지 확정한 결과는 아니다.

Worker의 로컬 Whisper 디코딩을 명시적인 beam search 5로 변경했다. 입력 변환·음량·반복 제외·무음 기준·모델 버전은 유지한다. 다른 모델로의 자동 재시도나 외부 서비스 전송을 추가하지 않았다. 모델 메타데이터에 실제 numBeams와 precision을 기록한다. 회귀 검사 39개와 합성 5초 무음의 빈 결과/경고 반환을 확인했다.

수정 후 원본 M4A의 실제 앱 요청 NAS `62a330ef-9d17-455b-9de0-1276002f20ec`, Worker `4d365b14-6bf9-44e2-8cd1-4fd8592cdc60`가 완료돼 한국어 가사가 표시됐다. 모델 단계 8.488초, 최대 할당 VRAM 3617.85 MiB, 예약 VRAM 3904.00 MiB, 자식 RAM 4302.34 MiB였다. 앱 새로고침 후 NAS 상태 재조회에서도 같은 결과를 확인했다. 단어 및 마지막 구절 오류는 남으며 전체 가사 정확도로 일반화하지 않는다. 비교 실험의 4.92% 오류율은 이번 실제 앱 결과의 수치가 아니다.

완료 후 Worker의 원본 샘플 필드와 자식 입력 파일 제거를 확인했다. 진단용 브라우저 WAV 복사본도 측정 후 제거했다. 개인 가사와 상세 실험 출력은 무시된 로컬 진단 폴더에만 보관하며 공개 문서에 전체 가사를 넣지 않는다. 제목·가수 검색은 이번 검증에 포함하지 않았다. 추가 GitHub 커밋·버전 출시는 아직 수행하지 않았다.


## 1.26.1 최종 통합 검증 — 2026-10-06

출시 변경은 Astro A50 등 녹음 장치 선택·입력 음량 표시, 브리지 상태 파일의 접근 거부 복구, 고정 Whisper turbo의 float32/beam search 5 적용, 인식 완료 안내 문구 수정이다. 앱/package/lock 버전은 1.26.1로 맞추며 기존 저장·백업 형식은 유지한다. 음악 런타임·스크린샷·빌드 산출물은 Vite 소스 감시에서 제외했다. 수정 전 개발 HTTP 응답이 65초 제한을 넘겼고 수정 후 첫 응답은 200/5.52초였다. 생성 파일 감시가 실제 로그에서 확인됐으나 다른 시스템 조건의 영향까지 배제한 보편적인 성능 벤치마크는 아니다.

인증된 NAS API에서 실제 모델로 5초 연주곡 → 10초 한국어 보컬 → 제목 검색+받아쓰기 동시 처리 → 5초 연주곡을 순차 실행했다. 작업 ID는 각각 `940f1277-f8f2-4453-b603-ea3676c55a0c`, `7640fc1b-c213-46c3-b0a6-eab0c6d25f83`, `fb07f946-794b-4e67-9c29-b9a23833fa93`, `05ebcc62-3c21-4aea-a25c-e100ce38807d`이며 모두 완료됐다. 대기 중 별도 120초 요청 `e4c3a7c7-7592-4ba7-82f8-2631f2d38189`는 취소됐다.
